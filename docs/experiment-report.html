01 / Domain

应用场景：为什么是挂号，以及它为什么需要这套东西

面试官的第一个问题永远是「这个系统给谁用」。所以这一节放在最前面。

放号是真实存在的瞬时洪峰：各医院普遍在固定时刻（6:00 / 7:00 / 提前 7 天）统一放号， 几万人在同一秒争抢几十个专家号。这个场景对系统的要求和电商秒杀几乎一致，但约束更硬： 超卖意味着现场多一个挂不上号的病人，少卖意味着公共医疗资源被白白浪费。

为什么排除了票务选座

票务的域更丰富，但座位不可互换——A5 不能借调给想要 B3 的人。 这会废掉整套已经验证过的三层库存与桶间借调。挂号的号源在排班维度可互换、 具体就诊时间是发号后分配的，所以既有真实业务复杂度，又保住了引擎前提。 这个取舍本身就是一次架构判断。

三类岗位的不同讲法

  • 业务后端：场景是限量号源的放号洪峰。核心是三层库存把 95% 的扣减挡在 Redis 之外，同时用五条可执行等式保证正确性——这套等式真的抓到过 bug。
  • 中间件 / 平台 / SRE：解决的是大促当天限流阈值靠人盯盘手调。做完发现真正难的是控制律：第一版因为判据看积压水位不看趋势，阈值被砍了 73 倍。
  • AI / Agent：关心的是让 LLM 能改生产参数而不出事。数据面完全没有 LLM，所有提案必须过白名单、钳制、dry-run、审计、回滚，Agent 挂掉自动退化为纯规则。

02 / Layering

引擎与业务域分离

引擎不该知道自己在卖号还是卖鞋。接口收窄成两个概念， 这样同一套验证过的代码换个域就能跑限量首发或选课。 

clinic 业务域   医院/科室/医生/排班/患者/预约单 · 六状态机 · 超时释放 · 退号 · 风控
      │
      │  poolId（库存池 = 排班 ID）   holderId（竞争者 = 患者 ID）
      ▼
inventory 引擎   三层库存 · 桶间借调 · 号段租约 · Lua 原子扣减 · Stream 削峰 · 一致性校验
      │
      ▼
control plane    L0 AIMD 规则 · L1 Agent · 护栏五件套 · 热配置

分离动作本身是一次 223 处、22 个文件的机械重命名（itemId → poolId、 userId → holderId），编译器全量校验，风险低但收益是引擎变成真正可复用的组件。

整个升级里最优雅的一处复用

引擎的租约本来解决「实例宕机后，它手里未售的本地号段必须还回桶」。 业务侧的「患者预占了号但没付钱，必须还回池子」是同一个形状的问题—— 差别只在持有者从「应用实例」变成「预约单」，续约从「心跳」变成「支付」。 所以两者共用同一套归还 Lua，只是多一类 holder： instance:<id> 和 appt:<id>。

P6 为什么「按预期失败」是好结果

04 / Business Loop

业务闭环：从抢号到退号的六状态机

这是「完整项目」相对「压测 demo」最关键的补齐。没有超时释放， 所有没付钱的人都白占着号，号池会被慢慢耗空而实际一个都没卖出去。 

[抢号成功] → PENDING_PAY ──支付──→ BOOKED ──就诊──→ COMPLETED
                  │                   │
                  │超时(10min)         ├─退号─→ REFUNDED    归还号源
                  ↓                   └─过期未就诊─→ NO_SHOW  不归还，计违约
              EXPIRED  归还号源
归还号源的三条路径。NO_SHOW 不归还是这个垂类必须想清楚的一点。
状态转移触发归还号源为什么
PENDING_PAY → EXPIRED3 秒定时扫描归还最常见，占绝大多数
BOOKED → REFUNDED患者主动退号归还有时限与退费规则
BOOKED → NO_SHOW就诊时段结束扫描不归还号源价值是「某时间点某医生的接诊能力」，时间过了就消失了，还回池子也没人能用。这和电商退货回库语义完全不同

闭环实测（50 号源小池，逐步走完状态机）

抢 5 个号            号源守恒  50 == 26(桶) + 19(实例持有) + 5(占号预约) + 0
支付 1 个            桶不变（号本来就被这张单占着）
退号 1 个            桶 26 → 27，占号 5 → 4
超时释放剩余 4 个     PENDING_PAY 4 → EXPIRED 4，占号 0，守恒残差 0
顺序不能反：先改 MySQL 状态，再还 Redis 号源

反了会超卖：先把号还回池子、还没改状态时进程挂掉，号被别人抢走， 而这张单在数据库里仍是 PENDING_PAY —— 一个号卖了两次。

正确顺序的失败模式只是少卖，而少卖有兜底：等式③ 会报出残差，对账能把差额加回去。 在「可能超卖」和「可能少卖」之间，永远选可能少卖。

05 / Anti-Scalper

风控对照实验：零误判，压制强度随攻击强度上升

风控在 3 万 req/s 的热路径上，而这条路径的全部意义就是避免网络往返。 所以判据必须纯本地、O(1)、零分配。 这一节也是全报告唯一被推翻重测过的一节。

为什么用 Count-Min Sketch

  • HashMap<String, Counter>：几十万 key 就是几十万次分配，放号高峰 key 空间突然膨胀，GC 压力直接打到热路径；
  • Redis 计数：每请求一次 RTT，把本地号段省下的 RTT 又加回来了；
  • CMS：内存固定（4 × 65536 双缓冲，三个 sketch 共 12MB），O(1) 读写，零分配。

代价是它会高估。所以判据只能是「超阈值就怀疑」， 不能直接拉黑——高估意味着会冤枉真实患者。

高估不是「一点点」，它有确定的量级

任意 key 的估计值天然含有约 窗口内事件总数 ÷ width 个别人的计数， 因为每一行的 width 个计数器要分摊窗口内所有事件。这个数是噪声底， 而阈值必须远大于它，否则判据恒真。

第一版 width=8192、窗口跨 20 秒，压测 27,666 req/s 打进来 → 约 55 万事件 → 噪声底 ≈ 67，而阈值是 3。 于是 55 万个请求每一个都被判成高频，全部降权进 20/s 的慢车道。

更根本的一点：CMS 适合找「占总量一定比例的重头」，不适合判定绝对小数。 阈值 3 相对 55 万总量是 0.0005%，任何亚线性草图都分辨不出这个量级。 现在 width 加大 8 倍，并在估计值里减掉噪声底（count-mean-min 修正）； 看板直接暴露 cmsNoiseFloor 和 criteriaHealthy（噪声底 × 3 < 阈值）， 因为判据失效时成交数和误拒率都看不出来。

压制强度随攻击强度上升，而误判恒为零。 这比一个孤立的百分比更有说服力——它说明防御方向是对的：越用力刷，被压得越狠。 也正因为它是一条曲线而不是一个点，才能看出下面这个结构性限制。

为什么前 15 个请求必然放过 —— 这是能力边界，不是 bug

设备阈值 = 阈值 3 × DEVICE_PATIENT_LIMIT 5 = 15。 任何基于频次的检测器都必须先观察够样本才能判断，这段「宽限期」是结构性的。

想缩短它就得降低设备阈值，而一家五口共用一台手机、每人刷三次正好是 15 次—— 降下去就会伤到他们，而误判真实患者恰恰是这套设计最不能接受的失败方向。 要真正关掉这个窗口，得换信号（设备指纹信誉、账号年龄、实名核验）， 而不是继续调频次阈值。把这条边界说清楚，比给一个漂亮的单点数字更接近工程事实。

命中理由是可读的，运营能直接看懂：

设备频次 200 超设备阈值 15，而该患者在此设备上仅 1 次，疑似一机多号批量代抢
处置刻意是「降权」不是「硬拒」

挂号场景里误判一个真实患者的代价极高——可能是急需就诊的老人，被拒之后不会重试、 也不会投诉，只是挂不上号。而放过一个黄牛的代价是一个号源被倒卖。 两者严重程度不对称，所以命中风控的请求走慢车道： 仍然能抢，只是绝对速率被压到 20/s——攻击量越大，能挤过去的比例越低。

只有失约黑名单（累计 3 次失约限制预约 30 天）才会真正拒绝， 而那个判据来自持久化的行为历史，不是瞬时频次估计。

A 组 · AIMD 控制律：从超调到收敛

接哨兵的真正障碍不是 Spring 配置，而是 Docker 下哨兵默认上报容器内网 IP （172.18.0.4），而跑在 Windows 宿主机上的应用解析不到、也连不通。 症状极其隐蔽：哨兵自己一切正常、切换也确实发生了，客户端却永远拿不到能用的地址。

解法是让所有地址都走宿主机 IP，并且脚本必须做一次 「客户端视角验证」——从宿主机去问哨兵要地址，再直接连一次。 没有这一步，你会得到一套看起来完全健康的哨兵集群和一个不跟随切换的客户端。

07 / Defects

五十一个缺陷

其中 8 个是我在修别的 bug 时引入的——这类「修复引入的缺陷」不该藏起来， 它们恰好是最能说明验证机制有效的证据。

类别数量典型缺陷
校验器本身9 用 XPENDING 当排空判据导致假通过；算出负数；无法区分故障模式；等式③ 在新域算法失效；等式⑤ 混比当前量与累计量；等式⑤ 的展示判据与 passed 字段用了两套标准（五条全显示通过而 passed=false）；累计量组在没走 preheat 时口径不可比却报不一致；累计量组拿「一个号池的行数」比「所有号池的事件数」（Stream 是单条全局设计，压测时只有一个池有流量所以一直没暴露，在演示排班上挂一个号就立刻报不一致）；等式③⑤ 与超时释放任务存在采样竞态（归还是「先改状态、再还号源」两步，在途期间做非原子多点采样必然差几个，被报成「号源凭空消失」）
消费端6 监听容器静默取消订阅且不自愈；僵尸消费者累积；看门狗重建时泄漏连接；PEL 自愈要 4.75 小时
控制面4 积压判据看水位不看趋势导致严重超调；放行阈值无下限；P99 作为健康信号是循环论证；新参数没登记默认值导致控制面看不见
数据面正确性7 售罄状态缓存无 TTL；物理桶数随配置变化导致库存失联；归还号源落到非活跃桶；booked_slots 漏减导致永久漂移；放号先推 Redis 再记账（记账带上限条件，被拒时号已进桶 = 超卖暴露）；实验重置漏清 released_slots 导致排班永久放不出号；归还号源时不清一人一单判重，患者被永久挡在门外（号已放回池子给别人抢了，而超时未付款的患者再也约不了这个排班；schema 里那套 active_key 生成列本来就是为「退号后能重约」做的，被热路径上更靠前的判重挡成了不可达——和 L1 门控废掉 L2 是同一个形状）
风控4 L1 门控让 L2 在最该生效的场景不可达；慢车道速率绑定主限流导致降权无效；CMS 噪声底盖过阈值，风控在高峰期变成全局熔断器；阈值不随噪声自适应（第一版修复只加宽草图 + 减噪声底，仍不足，被单元测试推翻）
可观测性9 故障期间每请求打完整堆栈（1.6 万条）；日志去重键含 Lua SHA；缺瞬态采样导致故障注入等于白做；慢车道丢弃与主限流拒绝共用计数器和返回码（污染压测结论，还让 AIMD 对着自己无法影响的信号做反应）；运营看板读不到护栏的处置说明（字段名错，而功能全对）；对账留档去重漏掉了最会重复的那一类（拒绝类结论天生持续，每周期写一条相同记录，默认间隔下一天 2880 行——做去重恰好把最该去重的放过去了）；被驳回的提案审计里 oldValue 硬写 null（看不出「Agent 想从多少改到多少」，而这正是判断它靠不靠谱的依据）；非法取值的审计回显显示成「500 → 500」，看起来像一次无害的空变更，真相是有人试图设成 NaN；MCP 的 body 解析失败返回 Spring 默认错误体而不是 JSON-RPC -32700（协议层写了 -32700 却永远走不到——Jackson 在进入协议层之前就失败了；严格客户端会在解析响应时二次失败，拿到的错误和真正原因完全无关）
前端3 manualChunks 写包名抵消按需引入（1193KB → 163KB）；/app/ 子目录 404（Spring Boot 只对根路径找 index.html，vite dev 下发现不了）；「我的预约」拿不到医生姓名（接口不返回，页面无法辨认是哪张单）
实验工具链9 kill 校验假阳性（两次）；压测打错实例导致 P5 验证不了任何东西；PowerShell 编码与 stderr 陷阱（三次）；PS 5.1 不展开 JSON 数组导致循环静默空转（"已放号 0 个、跳过 0 个"，既不成功也不失败）；对照实验按 ID 区间统计而事件表含历史数据，报出不存在的误判；脚本读一个改过名的字段做判断，-not $null 恒为真造成假警报（同一模式第三次：前端读 guardNote、放号脚本读 id）
最危险的一类：伪装成成功的失败

51 个里有 15 个属于同一种模式——系统看起来完全正常，实际上已经不工作了： 校验器把「发出 75742 条、入库 0 条」判成全部通过；消费者静默停工但健康检查是 UP； kill 校验报告「已确认退出」而进程又活了 21 秒；PEL 以每分钟 100 条还债而外观等同卡死； 风控两组成交率都 100% 而判据从未触发；风控吃掉 95% 的流量而报告只显示「被限流拒绝」； 护栏的钳制说明消失而 accepted 和实际值全对； 放号脚本报「0 个成功、0 个跳过」；五条等式全显示通过而机器可读的 passed 是 false；非法参数尝试在审计里显示成「值没变」；退号成功而患者再也约不上，两边状态各自看都正常。

这类问题比崩溃危险得多，因为崩溃会叫，静默降级不会。 它们也解释了这个项目为什么值得做：写出功能只用了一小部分时间， 剩下的都花在建立「能发现自己坏了」的手段上。

把不变量写成断言：82 个回归测试

这 46 个缺陷里有 45 个是靠人工观察发现的——跑一下、看着数字不对、往回查。 而其中 11 个属于「看起来正常」那一类，正是因为没有任何东西会主动喊。 所以后来补了测试，而且刻意不追求覆盖率： 静默降级不是靠多测几个分支发现的，而是靠把不变量写成断言。

后端 112 个（JUnit 5，纯单元、不起 Spring 容器）+ 前端 34 个（Vitest， environment: 'node'，不引 jsdom）。全部针对纯逻辑单元。
测试守的不变量失守的后果
CountMinSketchTest 高负载下判据不能退化成对所有人恒真 52 万请求被误丢，而外部只表现为「成交偏低」
RiskControlServiceTest 阈值永远高于噪声底，且只能被抬高不能被压低 抬得不够 → 全员误判；抬过头 → 黄牛怎么刷都不触发（漏判没人投诉）
ApptStatusTest 「占号 / 已归还」覆盖全部状态且不重叠 等式③ 开始报「号源凭空消失」，而排查方向完全指不到状态机
McpProtocolTest 两条错误通道不能混：未知工具→协议错误，执行失败→isError 结果；通知绝不能有响应 混了模型就分不清「换个工具」和「换个参数重试」；给通知回响应会让严格客户端断开
GuardDeciderTest 该挡的挡住（白名单 / 越界 / 震荡幅度 / 冷却期），而人的明确指令绝不能被挡 护栏是唯一允许 LLM 改生产参数的地方。过度保守的护栏比失效的护栏更隐蔽——它返回 accepted=true
ReconcileDeciderTest 凡是「不该动手」的情况，一次都不能动手 误补一次 = 凭空造号 = 自己制造超卖，而超卖对患者是不可回退的违约
useServerClock.spec 倒计时用校准后的时间，不用 Date.now() 还能付的单显示「已超时」，服务端日志里什么都没有
useGrab.spec 退避带抖动；异常路径也要释放锁 固定退避一样能「重试成功」，只是所有客户端同步冲击——本地测不出来
唯一一个由测试发现的缺陷

CountMinSketchTest 写完当场推翻了一小时前的修复。 我手工验证过 A/B 对照（低负载）和 P1 压测（阈值 500），两个都通过就以为修好了。 测试直接测了我没验证过的组合——阈值 3 + 高负载—— 发现普通患者的估计值仍然是 4 > 3。

这正是测试相对手工验证的价值所在：我只会去验证我想到的场景， 而漏掉的恰恰是我没想到的那个组合。 修完之后同一条测试成了这个不变量的永久守卫。

七个能在面试里讲完整的叙事

Narrative 01 · 校验器

把「全部通过」判给了一个一条预约都没入库的系统

症状
压测跑完，五条等式全部显示通过。而 MySQL 里一条预约都没有。
根因
排空判据用了 XPENDING。它只统计「已读但未 ACK」的消息，还没被消费组读取的消息既不算 pending 也不算已处理。消费者根本没启动时 pending 恰好是 0，于是「发出 75742 条、入库 0 条、pending 0」被判成完美。
修法
未处理量改用「已发出 − 已处理」计算，并把「多处理」和「欠处理」分成两个方向分别报告。
复验
同样场景现在会报「还有 75742 条未处理」并阻止判定通过。

Narrative 02 · 消费端

应用健康检查一切正常，消费却已经永久停止

症状
积压不再下降，/actuator/health 返回 UP，日志里只有海量看起来无害的 WARN。
根因
Spring 的监听容器在 Redis 连接抖动时会取消订阅并终止轮询，且不会自己恢复。主从切换场景更彻底：应用连到只读副本，而 XREADGROUP 是写命令，每次轮询必然失败。
修法
看门狗按 isActive() 检测并先 cancel 再重建（不 cancel 会泄漏连接，形成「失效—重建」的自我强化循环）；错误处理器区分偶发抖动与结构性故障；顺着 cause 链识别 READONLY 并给出可执行建议。
复验
接哨兵后消费端在切换中全程存活；日志从 187,779 条 WARN 降到 263 条。

Narrative 03 · 控制面

控制器把放行阈值砍了 73 倍，而积压全程都在下降

症状
阈值从 20000 崩到 275，误拒率 99.2%，连续 12 次降速、零次上调。
根因
降速判据只看积压的水位。控制周期 1 秒，而积压排空要几十秒——执行器比被控对象快 30 倍。日志里那一列积压数字全程单调下降，说明第 2、3 刀之后每一刀都是纯浪费。
修法
判据从「水位」改成「趋势」：只要积压在下降就不再砍。再加一个由实测排空速率决定的阈值下限。
复验
降速 12→5 次、上调 0→5 次，同延迟水平下成交 +27.7%。

Narrative 04 · 实验方法

故障注入报告「已确认生效」，而目标进程又活了 21 秒

症状
P5 连续两轮报告「全部等式通过」，但压测器异常数是 0——如果实例真在压测中途死了，后半程请求不可能全部成功。
根因
满载（3 万+ req/s）时，从「杀进程那一侧」观察的每一种判据都会假阳性：Get-Process 瞬时返回 null，端口枚举失败，健康检查的 2 秒超时在服务器饱和时本来就会超时。
修法
改用唯一可信的证人——压测器自己的异常计数。它是真正在和服务器对话的一方；异常为 0 就判定本轮数据无效、不许写进实验表格。
复验
改用 90 秒时长后观测到 933 次失败，故障落地确认；租约回收了 10 个本会少卖的号源。

Narrative 05 · 风控

分层风控的「按需触发」，把最该抓的场景变成了盲区

症状
对照实验里正常患者和黄牛两组成交率都是 100%，风控判据从未触发。
根因
我把设备判据（L2）门控在「患者频次超阈值」之后。而黄牛一机多号时每个患者的频次都很低（各请求两三次），高的是设备频次——门控之后 L1 判定通过、L2 根本没机会跑。我把 L2 门控在了它唯一能发挥作用的场景之外。
修法
患者维度和设备维度都在 L1 里算，任一超阈值才升级到 L2。两个 CMS 成本完全一样，没有任何理由门控其中一个。
复验
A 组 50 患者零误判，B 组黄牛 25 条 L2 命中、成交从 40 降到 26。（当时记录的「降到 12」是被下面 Narrative 07 的噪声污染的数字，已修正。）

Narrative 07 · 风控 · 本报告唯一被推翻的结论

把「压制 70%」写进简历之后，才发现那是噪声，而同一批噪声在误判所有人

症状
回归压测时发现成交只有 23,814，而三小时前同参数是 76,819。 报告显示「被限流拒绝 528,224」——数字本身没错，误拒率也确实高， 一切都像是控制面把限流砍狠了。
根因
两层原因叠在一起，任何一层单独都不足以看穿：
① CMS 的噪声底盖过了阈值。估计值天然含有约「窗口事件数 ÷ width」个别人的计数。 width=8192、窗口跨 20 秒、27,666 req/s → 55 万事件 → 噪声底 ≈ 67，而阈值是 3。 于是每一个请求都被判成高频，55 万个全部降权进 20/s 的慢车道，丢掉 52 万。
② 慢车道丢弃和主限流拒绝共用同一个计数器和同一个返回码 4290。 所以风控吃掉的 95% 流量被报成「限流拒绝」，而 AIMD 读到「误拒率 99.9%」 就一路砍限流（20000 → 6860）——控制面在对一个自己根本无法影响的信号做反应。
更坏的
这个噪声同时污染了三个月前就写进简历的那个数字。 「黄牛产出下降 70%」看起来是好结果，实际上是噪声把设备频次提前推过阈值造成的—— 而同一批噪声也在误判所有正常患者。一个漂亮的数字和一个严重的缺陷， 是同一个原因的两面。
修法
width 加大 8 倍到 65536（内存 1.5MB → 12MB，仍然固定、不随 key 数量增长）； 估计值里减掉噪声底（count-mean-min 修正，放弃「永不低估」换掉 100% 误判—— 这个取舍和风控既定原则一致：误判急需就诊的患者，代价远高于放过黄牛）； 新增 RISK_DEMOTED(4291) 与独立计数器，把两种「稍后再试」在可观测性上彻底分开； 看板暴露 cmsNoiseFloor 与 criteriaHealthy； 压测器和实验脚本在风控丢弃 ≥1% 时主动报警， 并把本轮风控阈值打进结论行——之前风控静默吃掉 95% 流量而报告毫无痕迹， 根因就是没人声明过这个前提。
复验
同参数成交 23,814 → 83,802（3.5 倍），风控丢弃 0%，噪声底 67 → 1， 五条等式全过。风控本身改用专门的 A/B 脚本标定，得到第 05 节那条随攻击强度上升的曲线。
后续
上面那个修复其实还不够，而是被单元测试当场推翻的。 我手工验证过 A/B 对照（低负载，噪声底 0）和 P1 压测（阈值 500），两个都通过就以为修好了。 而 CountMinSketchTest 直接测了我没验证过的组合——阈值 3 + 高负载—— 立刻发现普通患者的修正后估计值是 4，仍然超阈值 3。
数学上这是硬限制：减掉噪声底只消除了均值，残余波动仍在若干计数单位量级， 而阈值 3 本身就在这个量级里。所以真正的修复是让阈值自适应噪声底 （取配置值与 3×噪声底的较大者）：低负载时行为完全不变、A/B 结论仍成立； 高负载时阈值自动抬到噪声之上，普通患者放行而黄牛依然远超设备阈值。
这个抬升也符合业务直觉：放号瞬间人人都在高频重试，判据本来就该放宽； 平峰期同样的频次才是异常。把「随负载放宽」做成结构性质， 比指望运营在洪峰时手动调阈值可靠得多。
实测：生产默认阈值 3 + 高压画像，风控丢弃从 95% 降到 12.2%， 而残余的 12.2% 经查是真实尾部——理由写的是「频次估计 7 超阈值 6」， 压测流量里确实有患者在窗口内请求了 7 次，判成高频是正确行为。
这是整个项目第一个由测试而不是由观察发现的缺陷。
教训
性能画像测不出风控好坏，风控画像也测不出引擎性能。 高压画像是「20 万患者各请求两三次」，在患者频次判据看来就是全员高频。 两者必须分开跑，而且每轮报告都要写明本轮的风控阈值。 更一般地：近似数据结构必须把自己的误差量级暴露出来， 否则它会在最需要它工作的负载下安静地失效。

Narrative 06 · 自己引入的

修「日志放大」的时候，把日志放大了 33 倍

症状
为解决「故障期间每个失败请求打一条完整堆栈（1.6 万条）」，加了按异常类型去重的限流。结果日志从 3.4 万行涨到 111 万行。
根因
去重键含 root message，而 Redis 报错带 Lua 脚本的 SHA 和行号（script: 6b8f4637..., on @user_script:34）。键一直在变，于是每条都被判成「新类型」并打完整堆栈。
修法
把 SHA、十六进制、数字都折叠成 # 再做键；另加一个与键无关的硬性速率上限（5 秒最多一条堆栈）——归一化总会漏掉某种变体，兜底能保证漏掉了也不会炸。
复验
同场景日志 111 万行 → 1,774 行 → 接哨兵后 228 行。

  • 实现预约单六状态机与号源超时释放（未支付 10 分钟自动归还号池）， 复用引擎的租约归还机制实现两类持有者统一回收；针对本地预扣引入的「少卖」缺陷设计号段租约， 并实现五条可执行一致性等式（不超卖 / 不少卖 / 号源守恒 / 链路守恒 / 交叉校验）。 在实例 kill、MySQL 冻结、Redis 主从切换等 4 类故障注入下均为零超卖、零少卖， 其中节点故障轮回收 10 个本会变成少卖的号源。
  • 实现三层黄牛识别：本地 Count-Min Sketch 做频次估计（固定 12 MB， 热路径零 Redis 调用）、设备指纹关联分析、失约黑名单；处置采用慢车道降权而非硬拒 （误判急需就诊患者的代价远高于放过黄牛）。对照实验：正常患者 50 人零误判， 模拟黄牛一机代抢产出下降 35%→67%（随攻击强度上升）。 排查并修复该模块的关键缺陷：CMS 噪声底（窗口事件数÷width ≈ 67）远高于判据阈值（3）， 导致高峰期全部请求被判为高频、风控退化成全局熔断器； 以扩宽草图 + count-mean-min 修正解决，并把噪声底作为「判据是否可信」的指标暴露到看板。
  • 构建双层流量控制面：L0 AIMD 规则控制器秒级止损，L1 LLM Agent 经 MCP 读指标与 Trace 做归因与参数提案， 配套白名单、区间钳制、dry-run、变更审计与一键回滚，Agent 不可用时自动退化为纯规则。 修复控制律超调缺陷（判据由积压水位改为趋势）后，同参数同延迟下成交提升 27.7%， 放行阈值最低点从 275 回到 3,294。
  • 以混沌实验验证架构取舍：Redis 主从切换实测异步复制丢弃 14% 的 Stream 数据而 MySQL 预约零丢失， 据此确认「Redis 只做预扣与削峰、MySQL 才是账本」；接入 Sentinel 感知客户端后丢写降至 0.6%、 请求失败下降 98.7%。全程定位并修复 51 个缺陷， 其中 5 个属于「系统看起来正常但已停止工作」的静默降级。
写简历时必须同时说清的事

所有数字都来自单机 Docker 环境（压测器、应用、Redis、MySQL 同机）。 面试时主动说明，并把重点放在「同环境下改动带来的差值」和「故障注入下结论是否仍成立」—— 这两件事才是可迁移的能力证明。绝对吞吐在单机同机压测下没有说服力，硬吹是扣分项。

09 / Drill

面试问答

这些题的答案里都有具体数字，而不是「我觉得应该」。

为什么做挂号而不是电商秒杀？

三个理由，第三个是技术判断：

  • 约束更硬：超卖意味着现场多一个挂不上号的病人，少卖意味着公共医疗资源浪费。这让一致性校验器有存在理由，而不是过度设计。
  • 域更完整：实名制、退号规则、失约黑名单、分时段就诊、黄牛问题，天然需要状态机和风控，不是硬加的。
  • 号源可互换：同一排班内的号完全等价，所以三层库存和桶间借调能成立。我排除了票务选座——座位不可互换，A5 不能借调给想要 B3 的人，那会废掉整套引擎。具体就诊时间是发号后分配的，不是抢号时选择的。
你说零超卖，怎么证明的？

五条可执行等式，压测结束自动断言，不通过就让实验失败：

  • 不超卖：预约数 ≤ 总号数
  • 不少卖：售罄时刻预约数 = 总号数
  • 号源守恒：总号数 = Σ桶剩余 + Σ实例持有 + 占号预约数 + 已发出未落库
  • 链路守恒：已发出 = 已入库 + 重复 + 超卖拦截 + 死信 + 未处理
  • 交叉校验：占号预约 = 排班已占（当前量）；落库预约 = 消费入库（累计量）

关键是这套等式真的抓到过 5 个 bug，包括最早的版本因为用 XPENDING 当排空判据， 把「发出 75742 条、入库 0 条」判成了全部通过。我会主动讲这个失败—— 「校验器自己出过 bug 并被修好」比「校验器一直很完美」可信。

未支付的号怎么放回去？和实例宕机归还是一回事吗？

是同一个形状的问题，所以共用同一套机制，这是整个设计里我最满意的一处复用。

引擎的租约本来解决「实例宕机后手里未售的本地号段必须还回桶」，否则库存凭空消失。 机制是 Redis Hash 记录 holder → 持有量 + 到期时间，心跳续约，过期由巡检幂等回收。

业务侧「患者预占了号但没付钱」差别只在持有者从「应用实例」变成「预约单」、 续约从「心跳」变成「支付」。所以 holder 多一类前缀就复用了同一套归还 Lua。

但归还的桶范围和领取不一样，这里踩过一个 bug：领取时借调会扫全部 32 个物理桶， 所以传 MAX_BUCKETS 安全；归还如果落到非活跃桶，直连请求永远命不中， 号源等于半失联。归还必须落在活跃桶范围内。

失约的号为什么不还回池子？

因为号源的价值是「某个时间点某位医生的接诊能力」，时间过了这个能力就消失了， 还回池子也没有任何人能用它。

这和电商「退货回库」的语义完全不同——商品退回来还能卖给别人，而周三上午 8:15 的号 到周三下午就是废的。所以 NO_SHOW 只计违约次数（累计 3 次限制预约 30 天），不归还号源。

这一点如果搞错，一致性等式③ 会永远不平——因为你把一个已经消失的号算进了「可用」。

风控怎么在 3 万 QPS 的热路径上跑？

分层，成本递增、按需触发。关键约束是这条路径的全部意义就是避免网络往返——本地号段把 95% 的扣减挡在 Redis 之外，风控再加回 RTT 就白干了。

  • L1 频次：每请求都跑，本地 Count-Min Sketch，O(1)、零分配、零 I/O。用 CMS 而不是 HashMap 是因为几十万 key 的对象分配会把 GC 压力打到热路径上；
  • L2 行为：只在 L1 标记后跑。设备指纹关联、请求间隔规律性；
  • L3 黑名单：必须对每个请求生效，所以不能查库——本地缓存的 Set，定时从 MySQL 刷新。黑名单以百计，放得下。

CMS 会高估，所以判据只能是「超阈值就怀疑」，绝不能直接拉黑—— 高估意味着会冤枉真实患者。

而高估的量级是可以算出来的，这是我在这个项目里学到最有用的一件事： 任意 key 的估计值天然含有约「窗口事件数 ÷ width」个别人的计数。 我最初 width=8192、窗口跨 20 秒，压到 27,666 req/s 时噪声底是 67，而阈值是 3—— 于是每一个请求都被判成高频，风控在最该工作的高峰期变成了全局熔断器， 而外部表现只是「成交偏低、误拒率高」，完全看不出风控参与了。

修法是扩宽草图 + 在估计值里减掉噪声底（count-mean-min）， 并把噪声底本身暴露到看板作为「判据是否可信」的指标。 更一般的教训：近似数据结构必须把自己的误差量级暴露出来， 否则它会在负载最高的时候安静地失效。顺带我也放弃了「永不低估」这个性质—— 当前行为是 100% 误判，比偶尔漏一个黄牛坏得多，而这个取舍和风控既定原则一致。

这里还踩过一个很有意思的 bug：最初把设备判据门控在患者判据之后， 而黄牛一机多号时每个患者频次都很低、高的是设备频次——我把 L2 门控在了它唯一能发挥作用的场景之外。 两个 CMS 成本完全一样，没有理由门控其中一个。

风控误判了真实患者怎么办？

这是我在这个项目里做的最重要的一个价值判断，不是技术选择。

误判一个真实患者的代价极高——可能是急需就诊的老人，反复刷新页面很容易触发频次判据， 被拒之后他不会重试、也不会投诉，只是挂不上号。而放过一个黄牛的代价是一个号源被倒卖。 两者严重程度不对称。

所以处置是降权而不是拒绝：命中风控的请求走慢车道，绝对速率被压到 20/s， 仍有机会抢到，但拿到大量号源在物理上不可能——实测黄牛刷 40 次还能成 65%， 刷 200 次就只剩 33%，越用力刷，边际收益越低。 只有失约黑名单才真正拒绝，而那个判据来自持久化的行为历史，不是瞬时估计。

慢车道这里也踩过一个 bug：第一版速率写成主限流的 5%，而主限流默认 20000， 算出来 1000/s 根本不叫慢，实测黄牛 80 个请求全部通过。而且绑定主限流本身就自相矛盾—— 号源是有限的，黄牛在平峰期刷走 40 个号，跟当时有没有人竞争无关。

Redis 主从异步复制会丢数据吗？你的系统受影响吗？

会丢，我实测了。哨兵 failover 时从库还没复制完就被提升，旧主库反向同步会丢弃多出来的数据。

直连配置下实测丢了 20,685 条 Stream 条目（14%），而 MySQL 的 147,364 笔预约一笔没丢。 这正是设计验证：Redis 只做预扣器和削峰缓冲，账本永远是 MySQL。

接 Sentinel 感知客户端后丢写降到 0.6%——客户端立刻重连新主库，只丢切换瞬间那一点。 剩下的 0.6% 是异步复制的固有代价，靠对账补偿收敛，不靠 Redis 强一致 —— 这个对账现在真的实现了（ReconcileService），不再是一句设想。

项目上线了吗？这些数字什么环境测的？

没上线，单机 Docker 环境。绝对吞吐在同机压测下没有说服力，我关注两件事： 同环境下改动带来的差值，以及故障注入后结论是否仍成立。

比如「成交 +27.7% 而 P99 不变」这个差值可信，因为两轮参数完全一致、只改了控制律； 「零超卖」是在 4 类故障注入下都验证过的，不是理想条件下跑通一次。

我也知道瓶颈在哪：消费端落库约 2,850 笔/秒是天花板，数据面能接的远比 MySQL 能写的多。 要提有效吞吐该动批量落库和行锁竞争，不是继续压 Redis。

10 / Self-healing

对账补偿：让校验器能自己动手

在这之前，一致性这条线是断的：五条等式能算出「号源凭空消失 37 个」、 能说出故障模式的名字，然后就没有然后了 —— 一个只报警不处置的校验器，在无人值守的时段等于不存在。

补偿的动作只有一行：把差额加回桶。 全部难点在「什么时候不该动手」——四道闸门，每一道都对应一种 「补偿自己造成事故」的方式。

判据抽成了纯函数 ReconcileDecider（无任何 I/O），16 个单测覆盖四道闸门 及其交互。留在 Service 里的话，测它要 mock 校验器、Redis、配置、 JdbcTemplate 四样东西，于是实际上只会测两三条主路径。
闸门规则不设会怎样
① 方向不对称 只自动补少卖，绝不自动补超卖 回收号源 = 取消一个真实患者的预约。可逆的方向可以自动化， 不可逆的方向必须留给人——和「让失败落在少卖那一侧」同一条原则
② 采样必须稳定 归还在途时不判定，而且不计入连续次数 只「不动手」不够：反复出现的采样偏移能凑够次数触发补偿， 而那个残差本来不存在 —— 补进去就是凭空造号
③ 连续同一个数 连续 3 次（约 1 分钟）看到同一个残差才动手 判据写成「连续都非零」会补到中间态上 —— 数字还在变说明系统还在动（消费在途、租约即将回收）
④ 单次上限 残差超过 100 只告警不动手 这种量级更可能是校验器自己算错了，补偿会把错误放大成超卖。 「我的判断可能是错的」必须编码进自动化里
补完立刻复验，否则会从少卖变成持续超卖

补偿之后马上再探一次。不复验的话，补偿动作本身有 bug 时会 每 30 秒重复补一次 —— 那就不是修好了少卖， 而是自动化在持续制造超卖。自愈逻辑必须能判断「我刚才那一下到底有没有生效」。

开关刻意不进热配置白名单 —— 这是比护栏更强的边界

控制面的 8 个热参数都能被 L1 Agent 提案修改，对账开关不在其中。 它不是「调大调小看效果」的性能旋钮，而是会直接改动号源账目的安全开关。 让模型能打开它，等于给它凭空造号的能力 —— 即使有护栏， 这个能力本身就不该出现在提案空间里。

护栏管的是「改到什么值」，白名单管的是「能不能碰」。 想打开对账得改配置并重启，这个摩擦是刻意的。默认也是关的： 一个还没建立信任的自动化应该先只观察 —— POST /admin/reconcile/run?dryRun=true 能看到它「会」做什么， 和控制面改参数的 dry-run 是同一个思路：改账目的动作必须能先预演。

11 / Known Gaps

已知缺陷与后续计划

主动写出缺陷是成熟度信号，而且这几条恰好都是不错的面试延伸话题。

  • 测试只覆盖纯逻辑单元。已有 146 个测试（后端 112 / 前端 34），刻意只覆盖两类东西：纯逻辑单元，以及「坏了不会报错」的不变量。而 Lua 脚本、Stream 消费、护栏、放号链路都还没有自动化测试，靠压测脚本端到端验证——这几处都需要 Redis + MySQL，得上 Testcontainers。护栏已经补上了——42 个单测，含 bug ⑪「参数永远调不动而接口仍返回 accepted=true」的回归用例。剩下没有自动化测试的是 Lua 脚本、Stream 消费、放号链路，靠压测脚本端到端验证。
  • 没有组件测试。「点按钮后变 disabled」这类渲染行为靠手点。需要 jsdom + @vue/test-utils，但这个前端的逻辑复杂度不在渲染上，优先级低。
  • 风控的宽限期无法用频次判据关闭。设备阈值 15 意味着黄牛前 15 个请求必然放过，而降低它就会误伤「一家五口共用一台手机各刷三次」= 正好 15 次的真实用户。要关掉这个窗口必须换信号（设备指纹信誉、账号年龄、实名核验），这是当前设计的能力边界。
  • L1 Agent 尚未做完整 A/B。L0 规则层已有前后对比数据，但「规则 vs 规则+Agent」的三组对比还没跑。Agent 链路可用但缺量化结论。
  • MCP 已实现标准协议（POST /mcp，JSON-RPC 2.0：initialize 版本协商 / tools/list / tools/call，22 个协议单测），任意 MCP 客户端可直接接入。stdio 传输仍未实现——Claude Desktop 这类本地宿主需要它，而它的难点不在协议而在「stdout 被日志污染」：stdio 下 stdout 就是协议信道，任何一行日志都会破坏帧。
  • Grafana 只配了数据源，大盘未建。指标已通过 Micrometer 暴露，建面板是刻意留给自己动手的部分。
  • 模拟支付，不接真实网关。要验证的是超时释放，而不是支付集成——真实网关的异步回调、对账、幂等是另一个题目。
  • 单机环境的固有局限。压测器、应用、Redis、MySQL 同机，网络 RTT 被严重低估——真实多机环境下本地号段的收益会比现在更大，而不是更小。
