# FlashPilot 前端

Vue 3 + Vite + Element Plus。患者端（挂号 / 我的预约）+ 运营看板。

---

## 跑起来

```bash
# 后端要先起（8090），前端才有数据
cd ..
mvn spring-boot:run
.\scripts\seed-demo.ps1    # 灌演示排班并放号，否则页面上一个号都没有

# 前端开发模式（热更新，改代码立即生效）
cd frontend
npm install          # 首次
npm run dev          # → http://localhost:5173
```

`npm run dev` 之后所有接口请求会被 Vite 代理到 `127.0.0.1:8090`，
所以代码里一律写相对路径（`/clinic/...`），不用管跨域。

```bash
# 构建到后端静态目录，之后 mvn package 出来的 jar 自带前端
npm run build        # → ../src/main/resources/static/app/
```

构建后访问 `http://localhost:8090/`（根路径会自动跳到 `/app/index.html`）。
**一个 jar 跑整个应用**，不用单独部署 nginx。

> ⚠️ 不能直接访问 `/app/` —— Spring Boot 的静态资源只对**根路径**自动找 index.html
> （welcome page 机制），子目录不做目录索引，`/app/` 会直接 404。
> 这个坑在 `npm run dev` 下发现不了（vite dev server 会做目录索引），
> 只有构建后交给 Spring Boot 托管才暴露。所以 static 根目录留了一个跳转页。

> ⚠️ 这台机器上有 Clash 代理（`HTTP_PROXY=127.0.0.1:7897`），而代理在大流量下不稳定
> （Docker 拉 MySQL 镜像时被掐断过好几次）。所以 `.npmrc` 里配了国内源，
> 装依赖时如果卡住，先 `$env:HTTP_PROXY=$null` 再 `npm install`。

## 代码怎么读

按这个顺序看，从「最该学的」到「常规 CRUD」：

### 1. `src/composables/` —— 四个坑都在这里

**这是整个前端最值得读的部分。**它们不是「前端技巧」，而是**分布式系统的约束反映到前端**
的结果，面试也常问。

| 文件 | 坑 | 一句话 |
|---|---|---|
| `useGrab.js` | ① 防重复提交 | 只置灰按钮不够，还要一层数据锁（按住回车、脚本驱动时 disabled 不参与判断）|
| `useGrab.js` | ③ 429 退避重试 | 限流是**正常态**不是错误；**抖动不能省**，否则所有客户端同步重试形成惊群 |
| `useServerClock.js` | ② 时钟校准 | 倒计时绝不能用 `Date.now()`；用户时钟偏快会让还能付的单显示"已超时" |
| `useCountdown.js` | ② 的下半 | 一个全局 ticker 驱动所有行；倒计时归零要刷新列表让服务端状态覆盖前端推算 |

坑 ④（状态机在 UI 上的表达）在 `views/MineView.vue` 的 `STATUS_META` 里——
六种状态各自允许什么操作集中定义，不散在模板的 `v-if` 里。

### 2. `src/api/client.js` —— 一个关键约定

后端**所有业务错误都走 HTTP 200 + `code` 字段**，只有传输层错误才是非 200。

所以前端不能用 HTTP 状态判断业务结果。"号已售罄"是 `200 + code 4001`，
按 `res.ok` 判断就会当成成功；反过来把它做成 HTTP 400，浏览器控制台会刷一片红，
而它其实是完全正常的业务分支。

这个设计不随意：秒杀场景里"售罄""限流""重复"都是**高频正常路径**，不该被当成异常。

### 3. `vite.config.js` —— 两处优化和一个我踩过的坑

**按需引入 Element Plus**（`unplugin-vue-components` + `unplugin-auto-import`）。
全量引入会把整个组件库打进主包，实测 1,193 KB。

**但我一开始把两个优化写成了互相抵消**：`manualChunks` 里写了 `element: ['element-plus']`，
等于告诉 Rollup"把这个包整体打成一个 chunk"，直接覆盖掉 unplugin 依赖的 tree-shaking。
结果 element chunk 926 KB，按需引入白配。

三轮实测：

| 配置 | 最大单包 |
|---|---|
| 全量引入 | 1,193 KB |
| 按需 + 错误的 manualChunks | 926 KB |
| 按需 + 只拆 vue | **163 KB** |

教训：`manualChunks` 只适合「确定整体都要用」的库（vue 运行时）。
对按需引入的组件库，让 Rollup 自己决定分包，不要插手。

### 4. `src/constants/clinic.js` —— 一条小规矩

后端枚举值 → 中文的映射表（职称、号别、时段）。

它最初写在 `BookView` 里，后来「我的预约」也要显示职称和号别，
如果照抄一遍，**同一个枚举值迟早会在两个页面显示成不同的中文**，
而这种不一致没有任何测试会报错，只有用户会发现。

判断标准就一句话：**一个映射表被第二个组件需要的时候，就该搬出来。**

注意它刻意**不**收预约状态的映射——状态不只是文案，还带着「允许什么操作」的业务规则，
那属于 `MineView` 的 `STATUS_META`，和纯翻译表不是一类东西。

### 5. `src/views/` —— 三个页面

| 文件 | 说明 |
|---|---|
| `BookView.vue` | 挂号：科室/日期筛选 → 医生卡片 → 抢号（坑 ①③）|
| `MineView.vue` | 我的预约：状态机表达（坑 ④）+ 支付倒计时（坑 ②）|
| `AdminView.vue` | 运营看板：KPI 语义色、排班放号、风控、黑名单、变更审计 |

**患者端和运营端的设计取向刻意不同**，这是信息设计的核心判断：

- 患者端是「读一段流程」：引导性强、一次做一件事、每步有明确下一步
- 运营端是「一眼扫状态」：先给结论、异常项高亮、自动刷新、危险操作二次确认

用同一套组件硬套两边都不好用。所以运营端的 KPI 用**语义色**（好/警告/危险）
而不是全部同色——运营要在 0.5 秒内看出哪里不对，而不是逐个读数字。

## 刻意没做的事

| 没做 | 为什么 |
|---|---|
| **Pinia** | 共享状态只有「当前患者 ID」一个，`provide/inject` 就够。什么时候该上？当状态开始有派生计算和跨页面同步修改需求时 |
| **TypeScript** | 学习阶段先把 Vue 的响应式和组合式 API 搞清楚，类型系统是下一层。真实项目建议上 |
| **history 路由** | 用 hash 模式，因为产物由 Spring Boot 托管。history 模式需要后端加"未匹配路径转发到 index.html"的规则；上 nginx 时改成 history 更好看，加一行 `try_files` 即可 |
| **组件测试** | 已有 34 个单测（见下节），但没有「点按钮后按钮变 disabled」这类渲染测试。那需要 jsdom + `@vue/test-utils`，而这个前端的逻辑复杂度不在渲染上 |

## 测试

```bash
npm test          # 跑一次
npm run test:watch
```

34 个测试，落在三个 composable 加接口封装上——**因为四个坑的逻辑都在那里**。
（后端另有 90 个，全项目 124 个。）

用 `environment: 'node'` 而不是 jsdom：要测的是退避算法、时钟偏移、倒计时边界，
一个 DOM 节点都不需要。唯一的麻烦是 `useGrab` 依赖 `@/api/client`（里面用了
`localStorage`），用 `vi.mock` 把整个模块换掉就绕开了，比引入整个 DOM 环境干净得多。

几条测试值得单独看，它们守的都是**不会报错、只会静默变错**的行为：

| 测什么 | 为什么这条容易坏 |
|---|---|
| 本地时钟偏快 5 分钟时 `now()` 被拉回服务端时间 | 没有校准的话，还能付的单显示「已超时」，而服务端日志里什么都没有 |
| 退避时长带随机抖动（跑 8 次至少两个不同值） | 固定退避一样能「重试成功」，只是所有客户端同步冲击——本地测不出来 |
| 4291 的退避基数明显大于 4290 | 两者都是「稍后再试」，混用不会报错，但会给风控喂更多证据 |
| 请求抛异常后锁也要释放 | 只在后端偶发抛错时出现，本地开发几乎碰不到，一旦发生按钮永久卡死 |
| 重复 `start()` 不叠加定时器 | 叠加了功能完全正常，只是几十行列表有几十倍开销 |

> 写这组测试时自己也踩了一个坑：有个用例里造了一个 `Promise.reject(...)` 却从没 await，
> 于是变成游荡的 unhandled rejection，被 vitest 归到**后面某个不相关的测试**头上报错。
> 测试里造出来的悬空 promise 会污染别的测试的结论，比测试本身失败更难查。

## 扩展方向（按性价比排序）

1. **抢号页加实时余量推送**（SSE 或 WebSocket）。现在是抢完刷一次，
   放号瞬间余量变化很快，轮询看不到。后端要加一个推送端点。
2. **运营看板加趋势图**。现在只有当前值，看不出"积压是在涨还是在跌"——
   而这恰好是后端 AIMD 控制律的核心判据（看趋势不看水位），前端也该这么呈现。
3. **TypeScript 化**。先从 `api/client.js` 开始，给接口响应加类型，收益最大。
4. **移动端适配**。挂号的真实流量绝大多数来自手机，现在的布局只是响应式，不是移动优先。
5. **组件测试**（jsdom + `@vue/test-utils`）。补「点击后按钮变 disabled」这类渲染行为，
   和现有的逻辑测试是两层。性价比排最后是因为逻辑复杂度不在渲染上。
